# 20 联机同步、大厅、地图传输与本地存档 / 回放 / 快照恢复一致性

## 本章覆盖范围

本章按参考引擎生产源码梳理两条互相衔接的链路，粒度到可复刻：

1. **联机链路**：协议分层与报文编解码、确定性锁步（命令帧 / 输入延迟窗 / 失步判定）、快照分片传输与暂存—校验—提交状态机、LAN 大厅状态机与席位选项、地图请求—通告—分片—校验—缓存提交、互联网协调 / 中继 / 匹配 / 社区 / 排名服务的接入点与平台边界、合作战役会话、观战席位与重连恢复。

# A. 联机

## 1. 协议分层

### 1.1 三层结构

参考引擎联机按「传输帧 → 会话信封 → 玩法载荷」三层组织，各层独立版本与魔数：

| 层 | 模块 | 职责 | 版本 / 魔数出处 |
| --- | --- | --- | --- |
| 传输帧 | `src/network/session/RuntimeLanTransport.h:19` | `RuntimeNetworkPacket { type(u16), payload(bytes) }`，帧化 TCP / UDP 发现报文 | `runtimeLanProtocolVersion = 1`，`runtimeLanMaximumPacketBytes = 1 MiB`（`RuntimeLanTransport.h:10,13`）；帧魔数 `CRTS`（`RuntimeLanTransport.cpp:39`），发现魔数 `CLAN`（`RuntimeLanTransport.cpp:41`） |
| 会话信封 | `src/network/protocol/RuntimeMultiplayerProtocol.h:285` | `RuntimeMultiplayerMessage { type, body }`，body 为消息 DTO 的 `std::variant` | 消息版本 `runtimeMultiplayerMessageVersion = 4`（`RuntimeMultiplayerProtocol.h:16`）；消息类型枚举见 `RuntimeMultiplayerProtocol.h:24-62` |
| 玩法载荷 | `src/network/lockstep/RuntimeMultiplayerGameplayCommand.h`、`src/network/lockstep/RuntimeMultiplayerLockstep.h` | 命令载荷 `CGCM`、命令帧 `CGLF`；快照 `CSNP/CSNC/CSNA` | 命令魔数 `CGCM`、版本 20（`RuntimeMultiplayerGameplayCommand.h:15-18`）；帧魔数 `CGLF`、版本 1（`RuntimeMultiplayerLockstep.h:16-18`）；快照三魔数（`RuntimeMultiplayerSnapshotTransfer.h:11-17`） |

**类型字节布局约定**（`RuntimeMultiplayerProtocol.h:293-295`）：定宽整数一律大端；字符串与字节数组带大端长度前缀；编解码失败时输出参数保持不变。会话信封内命令、状态哈希、存读提案等报文使用大端 U8/U32/U64 与 `uint32` 长度前缀（`RuntimeMultiplayerProtocol.cpp:13-50`）。对局设置（MatchSetup）与玩法命令使用 `uint16` 字符串长度前缀（`RuntimeMultiplayerMatchSetup.h:183-185`；`RuntimeMultiplayerGameplayCommand.h:350-352`）。

### 1.2 传输帧格式（LAN TCP）

帧头固定 12 字节，大端（`RuntimeLanTransport.cpp:584-621`）：

| 偏移 | 字段 | 类型 | 含义 |
| --- | --- | --- | --- |
| 0–3 | magic | u32 BE | `0x43525453`（`CRTS`），`RuntimeLanTransport.cpp:39,604` |
| 4–5 | version | u16 BE | 必须等于 `runtimeLanProtocolVersion = 1`，否则拒绝（`RuntimeLanTransport.cpp:608-611`） |
| 6–7 | type | u16 BE | 0 保留；高字节为消息版本，低字节为事件标识（`RuntimeMultiplayerProtocol.h:12-15`） |
| 8–11 | payloadSize | u32 BE | 载荷字节数，上限 1 MiB（`RuntimeLanTransport.cpp:616-619`） |
| 12… | payload | bytes | 会话信封序列化内容 |

解帧允许一帧之后保留下一帧字节；非法魔数 / 版本 / 超大帧仅断开出错对端，不解释 lobby / 玩法消息（`RuntimeLanTransport.h:121-123`；`RuntimeLanTransport.cpp:612-619,717-730`）。

### 1.3 LAN 发现报文

- 探测报文：8 字节头 = magic `CLAN` + version(u16) + kind=1(probe) + 保留字节（`RuntimeLanTransport.cpp:381-389`）。
- 通告报文：magic `CLAN` + version(u16) + kind=2(advertisement)，随后为 `RuntimeLanRoomAdvertisement` 文本字段（`RuntimeLanTransport.cpp:411-451`；结构 `RuntimeLanTransport.h:24-36`）。
- 浏览器只取数据报源 IP，不信任主机自报地址（`RuntimeLanTransport.h:38-39`）；通告记录默认 5000 ms 老化（`RuntimeLanTransport.h:87-89`；`RuntimeMultiplayerLobbyFlow.h:62`）。

`RuntimeLanRoomAdvertisement` 字段：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `roomId` / `roomName` / `hostName` / `hostAddress` | string | 房间 / 名称 / 主机名 / 主机地址 |
| `contentFingerprint` | string | 内容兼容指纹（文本形式） |
| `protocolVersion` | u16 | 协议版本 |
| `sessionPort` | u16 | 会话 TCP 端口，默认 `17816`；发现端口默认 `17815`（`RuntimeLanTransport.h:11-12`） |
| `playerCount` / `maximumPlayers` | u8 | 当前 / 最大人数 |
| `passwordProtected` | bool | 是否口令保护 |
| `lastSeenMilliseconds` | u64 | 最近见到时间 |

### 1.5 序号 / 校验 / 指纹兼容

**命令信封序号**：`RuntimeMultiplayerCommandPacket { tick, peerId, sequence, payload, timelineEpoch }`（`RuntimeMultiplayerSessionSystem.h:189-201`）。序号从正值开始，允许在最近 `runtimeMultiplayerCommandSequenceReorderWindow = 65536` 窗口内重排；更大初始值或跳变被拒绝，防止单包驱逐有界防重放历史（`RuntimeMultiplayerSessionSystem.h:192-196,47-48`）。每对端维护独立序号窗口 `PeerCommandSequenceWindow{peerId, highestAccepted, acceptedSequences}`（`RuntimeMultiplayerSessionSystem.h:412-416`）。

**兼容三元组**：`RuntimeMultiplayerCompatibility { protocolVersion(u32), protocolFingerprint(u64), contentFingerprint(u64) }`（`RuntimeMultiplayerSessionSystem.h:83-89`）。

- 会话协议版本 `runtimeMultiplayerProtocolVersion = 9`（`RuntimeMultiplayerSessionSystem.h:18`）。
- 协议指纹：把 LAN、消息、会话、设置、命令、锁步、快照各模块公开常量汇入清单，域分隔 FNV-1a 计算（`RuntimeMultiplayerCompatibilityFingerprint.h:118-138`）。清单字段以稳定数字 id 排列，32/64 位构建结果一致（`RuntimeMultiplayerCompatibilityFingerprint.h:27-29,30-106`）；清单版本 `runtimeMultiplayerCompatibilityManifestVersion = 160`（`RuntimeMultiplayerCompatibilityFingerprint.h:12-13`）。
- 内容指纹：对规范化后的资源组件（canonicalResourceId + bytes）做域分隔 FNV-1a，固定组件数与显式长度，避免拼接歧义（`RuntimeMultiplayerCompatibilityFingerprint.h:140-168`）。

**准入校验**：加入时 `validateCompatibility` 比对协议版本与两枚指纹（`RuntimeMultiplayerSessionSystem.h:313-315`）；不兼容在 `JoinAccepted` 前拒绝。

### 1.6 消息应用路径与安全边界

两条应用入口（`RuntimeMultiplayerProtocol.h:336-355`）：

1. `applyRuntimeMultiplayerMessage`：直连报文安全入口。解码与来源绑定检查先于会话触碰；`Leave/Ready/Command/StateHash/SaveLoadPrepare/SaveLoadApplied` 必须指名已绑定连接的 peer；`Start/AdvanceAuthoritativeTick/SaveLoadProposal/Commit/Abort` 额外要求主机绑定连接；`SnapshotChunk/Ack` 仅协调器可发，两条直连路径均拒绝（`RuntimeMultiplayerProtocol.h:322-335`）。
2. `applyTrustedCanonicalRuntimeMultiplayerMessage`：仅用于主机已认证、规范排序后的广播复制；不得用于不可信直连报文（`RuntimeMultiplayerProtocol.h:342-355`）。

应用结果 `RuntimeMultiplayerMessageApplyResult { decoded, accepted, changed, duplicate, type, stateHashFrameComplete, desync, saveLoadStatus, reason }`（`RuntimeMultiplayerProtocol.h:308-320`）。

### 1.7 对局设置（MatchSetup）线格式

**魔数与版本**：`runtimeMultiplayerMatchSetupMagic = 0x434D5354`（`CMST`），版本 3；字符串长度前缀为大端 `uint16`（`RuntimeMultiplayerMatchSetup.h:10-12,183-185`）。解包接受版本 2 与 3；版本 ≥3 才读取协作任务字段（`RuntimeMultiplayerMatchSetup.cpp:791-795,809`）。

**限额**（`RuntimeMultiplayerMatchSetup.h:13-34`）：成员 ≤16、席位 ≤8、载荷 ≤8192 B、peerId ≤64 B、显示名 ≤96 B、规范地图 id ≤256 B、游戏模式 ≤64 B、规则覆盖 ≤256 B、席位选项 ≤64 B；固定 tick Hz ≤240；初始资金 ≤2,000,000,000；初始单位 ≤1000；科技等级 ≤10；游戏速度 ≤6。

**席位与成员**：

| 结构 | 字段 | 出处 |
| --- | --- | --- |
| `RuntimeMultiplayerMatchMember` | `peerId`, `displayName`, `identity`(Combatant=1/Spectator=2) | `RuntimeMultiplayerMatchSetup.h:36-54` |
| `RuntimeMultiplayerMatchSlot` | `slotIndex`(0 基连续), `controller`(Human=1/Computer=2/Closed=3), `peerId`, `countryId`, `colorId`, `teamId`, `difficultyId`, `startPosition`(0=确定性随机,1..8 显式且唯一) | `RuntimeMultiplayerMatchSetup.h:56-79` |
| `RuntimeMultiplayerMatchMap` | `canonicalId`(规范资源 id，非本地路径；去空白、ASCII 小写、`\`→`/`), `contentFingerprint(u64)` | `RuntimeMultiplayerMatchSetup.h:81-88` |
| `RuntimeMultiplayerMatchRules` | `gameMode`, `rulesOverride`, `randomSeed`, `fixedTickHz=30`, `startingCredits=10000`, `startingUnits=10`, `techLevel=10`, `gameSpeed=1`, `shortGame=true`, `mcvRepacks=true`, `crates=true`, `superweapons=false`, `buildOffAlly=false`, `cooperativeMission` | `RuntimeMultiplayerMatchSetup.h:101-118` |
| `RuntimeMultiplayerMatchSetup` | `revision`(主机每次接受大厅修改 +1), `hostPeerId`, `map`, `rules`, `members`, `slots` | `RuntimeMultiplayerMatchSetup.h:120-130` |

**规范化与校验（事务性）**：先规范化资源 / 选项标识、修剪显示文本、成员按 peerId 排序、席位按 slotIndex 排序，再执行严格校验；校验只接受规范形式（`RuntimeMultiplayerMatchSetup.h:167-181`；`RuntimeMultiplayerMatchSetup.cpp:682-739,892-897`）。

**两枚设置哈希**：

- `runtimeMultiplayerMatchSetupHash`：对规范版本线镜像做 FNV-1a（`RuntimeMultiplayerMatchSetup.h:198-204`）。
- `runtimeMultiplayerGameplaySetupFingerprint`：便携玩法指纹。设置先规范化并完整校验；**不混入**房间 revision、主机 / 成员身份、显示名、人类席位 peer 绑定；覆盖地图身份 / 内容、全部撰写规则、席位形态 / 控制器 / 选项与起始位。已保存的确定性对局可重绑不同认证 peer 而不改变玩法身份（`RuntimeMultiplayerMatchSetup.h:206-217`）。

**启动投影**：`RuntimeMultiplayerMatchLaunchDescription` 去掉房间身份、显示名、本地路径与本地玩家标记；两台机器即使认证 peer 与文件布局不同，看到同一对局时权威投影相等（`RuntimeMultiplayerMatchSetup.h:152-165`；`RuntimeMultiplayerLaunchConfig.h:11-14`）。`RuntimeMultiplayerLaunchAuthorityProjection { gameplaySetupFingerprint, map, rules, slots }`（`RuntimeMultiplayerLaunchConfig.h:32-41`）；`RuntimeMultiplayerLaunchConfigResult { config, authority, fullRoomSetupHash, localPeerIsHost, localPeerIsSpectator }`，全房间哈希仅用于诊断，不作玩法权威（`RuntimeMultiplayerLaunchConfig.h:43-51`）。

### 1.8 协作任务随房间设置携带

`RuntimeMultiplayerCooperativeMission { mapId, scenarioFingerprint, playerCountries[], enemyCountries[] }`（`RuntimeMultiplayerMatchSetup.h:92-99`）。规则校验：普通模式不得携带协作任务；协作任务 mapId 合法、指纹非零；两阵营国家列表非空且 ≤64、无 `random`、无重复（`RuntimeMultiplayerCooperativeRules.inl:1-22`）。席位校验：协作模式必须恰好 4 个 A–D 席位；地图文件名与任务 id 一致；A/B 可为 Human 或 Closed，C/D 必须 Computer；起始位固定 1..4，队伍固定 1/2，国家必须在对应阵营列表内（`RuntimeMultiplayerCooperativeRules.inl:24-47`）。

### 2.2 命令帧（GameplayFrame）

- 帧魔数 `CGLF`，版本 1，帧头 8 B；每帧命令 ≤64；帧字节上限沿用命令载荷上限（`RuntimeMultiplayerLockstep.h:16-25`）。
- `RuntimeMultiplayerGameplayFrame { commands[] }`：命令顺序是撰写玩法输入，予以保留；规范化只作用于每条命令内部，不排序向量顺序（`RuntimeMultiplayerLockstep.h:27-33`）。
- 帧整数与命令字节长度固定宽度大端；编码先规范化副本，解码要求收到的字节已是规范嵌套载荷；失败不改输出（`RuntimeMultiplayerLockstep.h:56-77`）。

### 2.3 锁步配置与输入延迟

`RuntimeMultiplayerLockstepConfig { inputDelayTicks=2, maximumCommandsPerFrame=64, maximumFrameBytes }`（`RuntimeMultiplayerLockstep.h:39-47`）。

- 屏障从 `session.startTick()` 起；`startTick + inputDelayTicks` 之前的 tick 是确定性空输入预热屏障，照常应用与推进，模拟不跳变（`RuntimeMultiplayerLockstep.h:35-38`）。
- 输入延迟不得超过会话命令领先窗 `commandLeadWindowTicks`（默认 120，上限 600）；帧字节不得超过会话命令载荷上限（`RuntimeMultiplayerLockstep.cpp:463-473`；`RuntimeMultiplayerSessionSystem.h:45,112`）。

### 2.4 帧接纳流程

`RuntimeMultiplayerLockstepDriver` 内部分参与者 `Participant{peerId, participation, lastSequence}` 与存储帧 `StoredFrame{packet, frame}`（`RuntimeMultiplayerLockstep.h:193-203`）。接纳步骤（`RuntimeMultiplayerLockstep.cpp:553-659`）：

1. 绑定检查：驱动与会话绑定有效、成员关系仍匹配（`RuntimeMultiplayerLockstep.cpp:557-559`）。
2. 时间线代检查：`packet.timelineEpoch` 非零且等于绑定代；代过期拒绝（`RuntimeMultiplayerLockstep.cpp:560-563`）。
3. 身份检查：peer 必须是房间成员；旁观者不得提交锁步帧（`RuntimeMultiplayerLockstep.cpp:569-576`）。
4. 已完成 tick 不得重放：`tick < currentBarrierTick`，或等于屏障且已应用，拒绝（`RuntimeMultiplayerLockstep.cpp:577-583`）。
5. 观察已接纳帧路径：会话命令历史中必须仍保留该信封（`RuntimeMultiplayerLockstep.cpp:585-594`）。
6. 重复 / 冲突帧：同 tick 同 peer 已有相同帧视为重复接受；不同帧拒绝（`RuntimeMultiplayerLockstep.cpp:596-603`）。
7. 输入窗检查：`tick >= firstNetworkInputTick_` 且 `tick >= authoritativeTick + inputDelayTicks`，否则「错过固定输入延迟窗」（`RuntimeMultiplayerLockstep.cpp:605-613`）。
8. 字节上限检查（`RuntimeMultiplayerLockstep.cpp:614-618`）。
9. 帧解码：命令数与帧字节双重校验；失败不消费会话序号状态（`RuntimeMultiplayerLockstep.cpp:620-632`；`RuntimeMultiplayerLockstep.h:134-136`）。
10. 序号严格递增检查（`RuntimeMultiplayerLockstep.cpp:633-637`）。
11. 直连路径先提交会话 `submitCommand`；观察路径不再重复提交（`RuntimeMultiplayerLockstep.cpp:639-648`）。
12. 存储帧并按 `(tick, peerId)` 排序（`RuntimeMultiplayerLockstep.cpp:650-659`）。

### 2.5 屏障、权威推进与追赶边界

- `frameBarrierReady(tick)` / `inputHorizonReady()`：权威 tick T 推进前，每名战斗成员必须已贡献 T + `inputDelayTicks` 的帧，保证固定输入管线在接纳窗前移到 T+1 后仍可填充（`RuntimeMultiplayerLockstep.h:148-153`）。
- `canonicalApplyList`：屏障未就绪、tick 非当前或绑定失效时输出不变；输出按 peerId、再按该 peer 帧内撰写命令顺序排序（`RuntimeMultiplayerLockstep.h:155-161,91-98`）。
- `applyReadyTick(prevalidate, apply)`：整批事务性提交；回调返回 false 不完成当前锁步 tick，允许安全重试（`RuntimeMultiplayerLockstep.h:95-98,163-167`）。
- 推进与应用分离：`advanceHost` 在当前 tick 应用后才被接纳；传输可先广播完成（`RuntimeMultiplayerLockstep.h:169-174`）。客户端 `acknowledgeAuthoritativeAdvance` 复查输入窗并拒绝乱序复制推进（`RuntimeMultiplayerLockstep.h:176-182`）。
- **追赶上限**：命令领先窗 `commandLeadWindowTicks` 上限 600 tick；状态哈希滞后窗 `stateHashLagWindowTicks` 上限 600 tick（`RuntimeMultiplayerSessionSystem.h:45-46`）。帧序号重排窗 65536（`RuntimeMultiplayerSessionSystem.h:47-48`）。
- **失步处理**：失步由状态哈希帧判定（见 2.7）；锁步驱动自身状态哈希覆盖帧魔数 / 版本、输入延迟、限额、绑定代、起始 tick、首网络输入 tick、屏障 tick、预期权威 tick、屏障已应用标志、参与者与已存帧（`RuntimeMultiplayerLockstep.cpp:886-907`）。

### 2.6 本地意图路由

`RuntimeMultiplayerPlayerIntentRouter` 把本地 UI 操作转成权威命令：每条方法构造对应强类型命令体、规范化后恰好回调一次 capture；不直接改动权威模拟状态（`RuntimeMultiplayerPlayerIntent.h:79-81`）。

- 权威状态 `RuntimeMultiplayerPlayerIntentAuthorityState { spectator, terminal, localDefeated }`（`RuntimeMultiplayerPlayerIntent.h:21-29`）。
- 摆放意图（本地预览态）：`lane`, `productionSerial`, `buildingTypeId`, `cell`, `previewValid`；确认摆放只在 capture 接受规范 `PlaceBuilding` 命令后清状态（`RuntimeMultiplayerPlayerIntent.h:34-45,142-156`）。
- 超武意图：`superWeaponId`, `expectedTargetCount`(0/1/2), `targets[]`（保留顺序，两阶段超武目标含义不同）；capture 拒绝时完整缓冲保留，重试逐字重发（`RuntimeMultiplayerPlayerIntent.h:47-57,160-173`）。
- 选择集、相机格、菜单开关属本地 UI 态，永不触发 capture（`RuntimeMultiplayerPlayerIntent.h:177-184`）。

### 2.7 状态哈希与失步判定

`RuntimeMultiplayerStateHashReport { tick, peerId, stateHash, timelineEpoch }`（`RuntimeMultiplayerSessionSystem.h:203-210`）。聚合帧 `RuntimeMultiplayerStateHashFrame { tick, timelineEpoch, complete, desync, hostStateHash, reports[] }`（`RuntimeMultiplayerSessionSystem.h:212-221`）。

- 报告必须落在周期 tick：`(report.tick - startTick_) % stateHashPeriodTicks == 0`，`stateHashPeriodTicks` 默认 30、≤ 最大 tick；哈希不得为 0（`RuntimeMultiplayerSessionSystem.cpp:1287-1296`；`RuntimeMultiplayerSessionSystem.h:114`）。
- 帧完整且主机报告存在时，任一成员哈希 ≠ 主机哈希即标记 `desync`（`RuntimeMultiplayerSessionSystem.cpp:298-306`）；记录首个失步 tick `firstDesyncTick_`（`RuntimeMultiplayerSessionSystem.cpp:782-784`；访问器 `RuntimeMultiplayerSessionSystem.h:408-409`）。
- 滞后窗回收：早于 `authoritativeTick - stateHashLagWindowTicks` 的帧被清除（`RuntimeMultiplayerSessionSystem.cpp:1072-1083,1280`）。

### 2.8 运行时桥接

`RuntimeMultiplayerRuntimeBridge` 持有生产 LAN 会话，在大厅创建、移入 RuntimeShell、再挂载到一个活跃权威世界；套接字 / 会话状态永不进入世界哈希或快照（`RuntimeMultiplayerRuntimeBridge.h:139-142`）。

- 超时常量：初始加载 180000 ms；断线恢复 20000 ms（`RuntimeMultiplayerRuntimeBridge.h:32-35`）。
- 回调集 `RuntimeMultiplayerRuntimeCallbacks`：命令预校验 / 应用、当前已完成 tick、推进模拟、权威状态哈希、对局终局；以及主机独占的重连检查点捕获、快照暂存校验、快照提交、暂存丢弃、加载后代时间线重绑（`RuntimeMultiplayerRuntimeBridge.h:42-80`）。
- 可选外部有序传输 `RuntimeMultiplayerExternalOrderedTransport`：承载私有 LAN 会话（如认证互联网 TCP 中继）；普通 LAN 桥接不安装。实现必须保持流序并把服务 / 隧道 / 代理丢失上报为失败（`RuntimeMultiplayerRuntimeBridge.h:96-110`）。排名对局结果上报是可选、非确定性、一次性服务侧副作用；LAN 与普通互联网房间保持 false（`RuntimeMultiplayerRuntimeBridge.h:117-135,232-241`）。
- pump 排空传输，恰好提前 `inputDelayTicks` 供一空帧或撰写帧；只有主机响应 `requestHostAdvance`，客户端与旁观者只跟随规范主机消息（`RuntimeMultiplayerRuntimeBridge.h:224-230`）。

### 4.2 席位选项选择与校验

席位选项请求 `RuntimeMultiplayerLobbySlotOptionsRequestMessage`（`RuntimeMultiplayerProtocol.h:217-231`）：`peerId`, `requestId`, `expectedSetupRevision`, `slotIndex`, `countryId`, `colorId`, `teamId`, `difficultyId`, `startPosition`。结果 `RuntimeMultiplayerLobbySlotOptionsResultMessage`：`peerId`, `requestId`, `accepted`, `currentSetupRevision`, `reason`（`RuntimeMultiplayerProtocol.h:233-243`）。

### 4.3 大厅流程编排

`RuntimeMultiplayerLobbyFlow` 为 LAN 浏览器与直连互联网界面共享（`RuntimeMultiplayerLobbyFlow.h:23-26`）：

- 入口：`startHost`（可带 `ResumeSave` 恢复存档）、`startBrowsing`、`join`、`sendDiscoveryProbe`（`RuntimeMultiplayerLobbyFlow.h:43-57`）。
- 轮询：`poll(transportTimeoutMilliseconds)` 返回 `lobbyChanged / matchStarted / events[] / error`（`RuntimeMultiplayerLobbyFlow.h:15-21,65-67`）。
- 本地地图校验：`verifyLocalMap(localMapPath)` 读取本地文件并证明其与主机公布的规范地图逐字节一致；此后主机任一地图编辑都会使该证明失效并清除本地就绪，需重新 `Ready=true`（`RuntimeMultiplayerLobbyFlow.h:106-112`）。
- 缺失地图下载：`downloadMissingMap(localDataRoot, output)`；重复调用观察同一次请求，不发布部分文件（`RuntimeMultiplayerLobbyFlow.h:115-117`）。

### 4.4 地图传输状态机

地图传输复用快照的有界、未压缩分片引擎，但描述符从不提交世界 Save/Load 操作（`RuntimeMultiplayerMapTransfer.h:6-8`）。

**DTO**：

| 结构 | 字段 | 出处 |
| --- | --- | --- |
| `RuntimeMultiplayerMapRequest` | `requestId(u64)`, `map`(`RuntimeMultiplayerMatchMap`) | `RuntimeMultiplayerMapTransfer.h:9-13` |
| `RuntimeMultiplayerMapOffer` | `request`, `transfer`(`RuntimeMultiplayerSnapshotDescriptor`) | `RuntimeMultiplayerMapTransfer.h:15-19` |

**请求校验**（`RuntimeMultiplayerMapTransfer.cpp:20-30`）：`requestId` 非零；地图指纹非零；canonicalId ≤256 B 且以 `multimd/` 开头；规范化后 id 必须与请求一致，拒绝不安全 / 非规范资源 id。

**字节校验**（`RuntimeMultiplayerMapTransfer.cpp:40-50`）：非空且 ≤64 MiB；装入 `RuntimeMultiplayerContentComponent` 计算内容指纹，必须与房间公布的 `contentFingerprint` 一致。

**描述符身份绑定**：地图传输的快照身份以 `requestId` 为提案 id、Kind=Save、时间线代 1、屏障 / 快照 tick 0、令牌 `map-<requestId>`、两枚指纹均取地图内容指纹；Offer 描述符身份必须与请求一致（`RuntimeMultiplayerMapTransfer.cpp:6-17,35-36`）。

**大厅侧状态机 `RuntimeMultiplayerLobbyMapTransfer`**（`RuntimeMultiplayerLobbyMapTransfer.h:12-75`）：

- 主机侧 `HostPeer`：`request_`, `producer_`, `offerSent_`, `chunkSent_`, `startedAt_`, `chunkSentAt_`；每轮 poll 至多先 Offer 再一片，每片成功入队后才问下一片，发送失败停止该 peer 本轮 poll（`RuntimeMultiplayerLobbyMapTransfer.h:16-24,49-52`）。
- 输入 `Input { peerId, lobby, admitted, ready, currentMap }`；输出 `Action { handled, peerId, transferId, send, failure, reason, complete }`（`RuntimeMultiplayerLobbyMapTransfer.h:26-43`）。
- 客户端侧：`alreadyRequested` / `clientIncomplete` / `prepareRequest`；`requested` 只在 Ready=false 且请求成功入队后提交；`receiveClient` / `pollClient` 驱动 Offer → 分片 → ACK；`offer()` 与 `bytes()` 暴露已校验结果（`RuntimeMultiplayerLobbyMapTransfer.h:54-62`）。
- **重传 / 超时**：分片 ACK 驱动——生产者在当前片确切 ACK 被接受前重复返回同一片（见 3.2）；状态机使用 `steady_clock` 时间点记录请求 / 分片时刻（`RuntimeMultiplayerLobbyMapTransfer.h:14,22-23,74`）。传输层空闲与超时由外部 poll 时限与桥接超时约束（见 2.8）。
- **缓存提交顺序**：组装校验通过后，`storeRuntimeMultiplayerMapCache` 先核对 Offer 字节数、指纹、SHA-256 与地图字节校验，再写入本地数据根下 `multiplayer/maps/`；现有条目必须已合法，绝不覆盖无关文件、损坏条目或伪装缓存的链接（`RuntimeMultiplayerMapCache.cpp:63-89`）。缓存文件名 = 16 位十六进制指纹前缀 + `-` + 64 位十六进制 SHA-256 + `.map`；查找时按前缀匹配并逐文件重新校验（`RuntimeMultiplayerMapCache.cpp:43-60,92-108`）。路径安全：拒绝符号链接与 Windows 重解析点（`RuntimeMultiplayerMapCache.cpp:15-27`）。

口令不进入公开通告与规范玩法报文；纯辅助工具提供可移植 SHA-256 / HMAC 派生，不引入平台加密依赖（`RuntimeRoomPassword.h:11-14`）。

### 4.6 互联网服务端、凭据与 TLS 边界

**服务宿主 `RuntimeInternetServiceHost`**：自托管 TCP/TLS 互联网控制与中继服务；类本身不开 / 不播发 / 不转发 UDP；中继数据流只在两条独立认证 TCP 腿都被协调器接受、协调器发出 `ActivateRelayRoute` 后才释放（`RuntimeInternetServiceHost.h:107-110`）。

**宿主限额 `RuntimeInternetServiceHostLimits`**（`RuntimeInternetServiceHost.h:38-60`）：应用认证超时 5000 ms；协调器空闲超时 120000 ms；中继对空闲超时默认 0（不禁字节空闲过期，靠认证中继心跳 / TCP 关闭 / 租约 / 容量回收）；中继心跳 5000 ms；待处理中继 10000 ms；认证连接 ≤64、总连接 ≤768、协调器连接 ≤256、单 peer 协调器连接 ≤1、待处理中继腿 ≤512、活跃中继对 ≤256；防重放 nonce ≤8192、单 peer ≤128，保留 60000 ms。

**部署配置**（`RuntimeInternetServiceHostConfig.h:69-80`）：`serviceId`, `tls`, `coordinator`, `matchmaking`, `community`, `relay`, `limits`，外加单调时钟回调与凭据校验回调。`RuntimeInternetServiceHostDeploymentConfig { serviceId, listenPort, listenScope, publicRelayAddress, certificate, credentials, communityStatePath }`（`RuntimeInternetServiceHostConfig.h:69-80`）。严格 INI 解析：仅 `[Service]` 与 `[Credentials]` 各一次；`[Service]` 每个键恰好一次；凭据键为大小写敏感 peer id（`RuntimeInternetServiceHostConfig.h:82-95`）。

**凭据存储**：共享只读存储只保留 SHA-256 凭据摘要，原始客户端凭据永不进入部署配置（`RuntimeInternetServiceHostConfig.h:28-30,56-60`）。证书选择按存储位置（CurrentUser=1/LocalMachine=2）、存储名、SHA-1 指纹（20 B）（`RuntimeInternetServiceHostConfig.h:14-24`）。

**TLS 传输**：`RuntimeInternetTlsClient` / `RuntimeInternetTlsServer` 为增量出站 TCP + Schannel 握手；套接字在 `begin()` 后保持非阻塞，`poll()` 推进连接与握手（`RuntimeInternetTlsTransport.h:55-58`）。客户端配置含端点、服务名（证书校验恒用此名，不用 endpoint.address，即使 IP 字面量）、连接 / 握手超时、可选叶子证书 SHA-256 钉扎（钉扎是附加限制，不绕过 Windows 系统链与主机名检查）、吊销检查、私有信任锚（`RuntimeInternetTlsTransport.h:29-47`）。

> **平台边界（如实标注）**：TLS 后端绑定 Windows Schannel；非 Schannel 平台上客户端 / 服务端各入口返回 `"Runtime Internet TLS transport requires Windows Schannel"`（`src/network/transport/RuntimeInternetTlsTransport.cpp:1837,1847,1871,1885`）。参考引擎未提供 Linux / macOS 的 TLS 实现。README 亦注明 Linux TLS 的 Schannel 实现明确不支持（`README.md:13`；缺口表 #2，`01-源码清单与类层次.md:4102`）。

**服务端线协议**：线版本 1；nonce 32 B；凭据 16..4096 B；线帧上限 = LAN 包上限 + 16 KiB；缓冲 4 MiB（`RuntimeInternetServiceTransport.h:16-23`）。报文体含认证请求 / 确认 / 拒绝 / 协调器包（`RuntimeInternetServiceTransport.h:33-97`）。认证凭据不进入拒绝或确认帧（`RuntimeInternetServiceTransport.h:99-101`）。nonce 防重放窗口按服务域在已接受 TLS 连接间共享（`RuntimeInternetServiceTransport.h:128-130`）。

### 5.2 观战接入点

- 身份枚举：`RuntimeMultiplayerParticipationRole { Combatant, Spectator }`（`RuntimeMultiplayerSessionSystem.h:62-65`）；成员 `RuntimeMultiplayerRoomMember { peerId, displayName, role, participation, ready }`（`RuntimeMultiplayerSessionSystem.h:119-129`）。
- 容量：战斗成员 ≤8、旁观者 ≤8，合计 ≤16（`RuntimeMultiplayerSessionSystem.h:19-23`；`RuntimeMultiplayerLanSession.h:116-117`）。
- 旁观者挂载同一完整确定性世界，但不能捕获输入帧（`RuntimeMultiplayerRuntimeBridge.h:188-190`；锁步帧拒绝旁观者，`RuntimeMultiplayerLockstep.cpp:573-576`）。

### 5.3 互联网协调与中继

**控制报文 `RuntimeInternetControlMessage`**（`RuntimeInternetConnectivity.h:239-249`）：`type`, `transactionId`, `serviceId`, `roomId`, `senderPeerId`, `targetPeerId`, `body`。控制版本 3，控制包类型 `0x0101`，上限 64 KiB（`RuntimeInternetConnectivity.h:15-17`）。

**控制类型**（`RuntimeInternetConnectivity.h:198-217`）：`RegisterRoom=1`, `RegisterAccepted=2`, `RoomListRequest=3`, `RoomListResult=4`, `JoinRoom=5`, `PeerCandidates=6`, `PunchProbe=7`, `PunchAck=8`, `RelayRequest=9`, `RelayLease=10`, `RelayBind=11`, `RelayBound=12`, `Error=13`, `SealRoom=14`, `RoomSealed=15`, `CoordinatorHeartbeat=16`, `CoordinatorHeartbeatAck=17`, `ResumeRoute=18`。

**角色 / 候选 / 中继**：`Role { Host=1, Client=2, Spectator=3 }`；`CandidateKind { Host=1, ServerReflexive=2 }`；`RelayTransport { Udp=1, Tcp=2 }`（`RuntimeInternetConnectivity.h:30-44`）。候选体含端点、优先级；中继租约含连接 id、传输、端点、票据（`RuntimeInternetConnectivity.h:46-59,133-163`）。

**连接状态机**（`RuntimeInternetConnectivity.h:263-285`）：`Idle → RegisteringRoom / QueryingRooms / JoiningRoom → WaitingForPeer → Punching → RequestingRelayUdp / BindingRelayUdp → RequestingRelayTcp / BindingRelayTcp → UdpCandidateVerified / ConnectedRelayUdp / TcpTunnelBound → GameplaySessionConnected / RoomListReady → Failed / Closed`。

> 注意：UDP Punch/Ack 只证明一个 UDP 候选可达，**从不**作为 TCP 帧化会话的可用状态；中继包只能从租约选定端点投递；`GameplaySessionConnected` 必须在该路由规范 `JoinAccepted` 后才由隧道 / LAN 适配器上报（`RuntimeInternetConnectivity.h:274-276,394-411`）。

### 5.6 社区服务

社区线版本 3，包类型 `0x0103`，上限 64 KiB（`RuntimeInternetCommunity.h:17-21`）。操作枚举 `Login, RegisterProfile, Refresh, JoinChannel, SendChannelMessage, AddFriend, RemoveFriend, ReportQuickMatch, CreateClan, InviteClanMember, AcceptClanInvitation, RemoveClanMember, LeaveClan, TransferClanOwnership, QuickMatchHistory, AbandonQuickMatch`（`RuntimeInternetCommunity.h:46-63`）。响应种类 `Snapshot / ChannelMessage / Error / MatchHistory`（`RuntimeInternetCommunity.h:65-70`）。档案 `RuntimeInternetCommunityProfile` 含 peerId、显示名、注册 / 最近在线时间、胜 / 负 / 掉线、积分（默认 1000）、排名、在线标志（`RuntimeInternetCommunity.h:78-91`）。渠道、好友、聊天历史、天梯、新闻、clan 等限额见 `RuntimeInternetCommunity.h:22-44`。

### 5.7 服务适配器与客户端接入

`RuntimeInternetServiceAdapter` 接口窄于套接字抽象：互联网玩法路径是可靠 TCP 字节流，流程从不要求嵌入应用打开未认证 UDP 玩法路由（`RuntimeInternetLobbyFlow.h:15-18`）。必选方法：`authenticatedServiceId / authenticatedPeerId`、`sendCoordinator`、`openAuthenticatedTcpRelay`、`poll`、`close`；可选 `sendCoordinatorWithAdmissionProof`（不支持时带口令保护的注册 / 加入失败关闭）、`reauthenticateCoordinator`（不支持则协调器重连失败关闭）（`RuntimeInternetLobbyFlow.h:59-99`）。

### 6.1 保存文档解析

### 6.2 身份校验

**活动身份视图 `RuntimeSaveActiveIdentity`**（`RuntimeSaveIdentity.h:7-13`）：`campaignMode`, `defaultMapPath`, `campaignId`, `campaignMissionId`, `campaignSourceId`，全部为只读引用；规范化操作不保留到同步校验调用之外（`RuntimeSaveIdentity.h:5-6`）。

**规范化适配器 `RuntimeSaveIdentityNormalization`**：`mapIdentity(path)` 与 `campaignSourceId(source)` 由原有逻辑所有者提供；校验不捕获 / 替换其分配 / 文件系统异常（`RuntimeSaveIdentity.h:18-23`）。

**字段解码 `decodeRuntimeSaveIdentityField`**：优先读取编码键（十六进制解码，上限 32 KiB），空则回退遗留明文键；解码失败报 `invalid encoded save identity`（`RuntimeSaveIdentity.cpp:10-31`）。

**外部身份校验 `validateRuntimeSaveOuterIdentity`**（`RuntimeSaveIdentity.cpp:33-153`）：

1. 版本 <13：直接通过（`RuntimeSaveIdentity.cpp:40-42`）。
2. 版本 15（便携多人快照）：必须非战役模式且存在 `[MultiplayerSnapshot]` 段；信封绝不携带进程本地文件路径（`RuntimeSaveIdentity.cpp:43-53`）。
3. 遭遇战：活动地图身份不可为空；解码 `RuntimeSave` 段 `MapHex`（遗留 `Map`），经规范化后与活动地图比对，不一致报 `save belongs to a different map`（`RuntimeSaveIdentity.cpp:55-77`）；存在 `[Campaign]` 段时报 `save is a campaign mission`。
4. 战役模式：必须存在 `[Campaign]` 段且 `Mode` 规范化为 `CAMPAIGNMISSION`；比对 `CampaignHex/Campaign`、`MissionHex/Mission`；`SourceIdHex/SourceId` 非空时按规范化来源比对；campaign / mission 大小写不敏感比对（`RuntimeSaveIdentity.cpp:79-151`）。

### 6.3 候选状态加载事务

`RuntimeLoadTransaction` 为同步候选事务接口；适配器在执行返回前持有候选，提交不抛异常；设备重建在该发布之后，不能把已提交加载变成失败（`RuntimeLoadTransaction.h:5-7`）。

| 方法 | 语义 |
| --- | --- |
| `seedCandidate(forceVisionEnabled)` | 播种候选世界 |
| `materializeCandidate(savePath, error)` | 从保存路径物化候选；失败返回 false |
| `prepareCandidate()` | 候选就绪前准备 |
| `commitCandidate() noexcept` | 发布候选为权威（不抛异常） |
| `presentCommitted()` | 提交后呈现；异常被吞掉，不回滚提交 |
| `releaseCandidate() noexcept` | 先销毁动作、再销毁候选；正常返回与物化拒绝时都运行 |

执行器 `executeRuntimeLoadTransaction(transaction, savePath, error, forceVisionEnabled)`（`RuntimeLoadTransaction.cpp:5-37`）：

1. 注册候选生存期守卫，析构时 `releaseCandidate`。
2. `seedCandidate` → `materializeCandidate`（失败返回 false）→ `prepareCandidate` → `commitCandidate`。
3. `presentCommitted` 异常被捕获忽略。
4. `std::exception` / 未知异常统一转为 `load materialization failed: …` / `load materialization failed`，候选由守卫释放。

### 6.4 三条恢复路线复用的恢复内核与设备重建时机

三条路线——**本地存档**、**回放 Reset/世界恢复**、**网络快照暂存—提交**——共享同一恢复内核：

- 本地存档：`loadRuntimeState(session, path, error)`（佐证入口见 `RuntimeRecoveryConsistencySmoke.inl:120`）。
- 回放：`restoreRuntimeMatchReplayWorld(state, configText, state, tick, stateHash, error)`（`RuntimeMatchReplayRuntime.inl:220`；佐证 `RuntimeRecoveryConsistencySmoke.inl:123-124`）。
- 网络快照：`stageRuntimeMultiplayerSnapshot(session, bytes, descriptor, staged, error)` → `commitRuntimeMultiplayerSnapshotAuthority(session, move(staged))`（佐证 `RuntimeRecoveryConsistencySmoke.inl:126-128`）。

**设备重建时机**：按 6.3 事务边界，候选世界先在隔离候选内物化 / 校验，`commitCandidate`（网络路径即 `commitStaged` / `commitRuntimeMultiplayerSnapshotAuthority`）发布为权威之后才进行设备 / 呈现重建；提交后路径的失败不能回滚权威世界（`RuntimeLoadTransaction.h:5-7,15-18`；`RuntimeMultiplayerSnapshotSession.h:62-65`）。网络权威提交保留本地呈现态（相机偏移、选择集），不随快照重置（佐证 `RuntimeRecoveryConsistencySmoke.inl:127-130`）。

> 佐证说明：上述三路线函数名来自 `diagnostics/` 一致性夹具调用链；生产侧对应接入点为 `RuntimeLoadTransaction` 接口、回放恢复内核（`RuntimeMatchReplayState.inl` 私有主机恢复内核，被录制 / 查看器与恢复契约共同包含，`RuntimeMatchReplayState.inl:3-5`）与快照钩子（`RuntimeMultiplayerLanSession.h:212-237`）。

## 7. 回放封包、事件流与恢复一致性

### 7.1 封包格式

- 格式版本 1；单条记录载荷 ≤128 MiB；整文件 ≤8 GiB（`RuntimeMatchReplay.h:11-13`）。
- 文件头魔数 `CRTSRPLY`（8 字节），随后格式版本(u16) 与玩法命令版本(u16)；两者不兼容拒绝（`RuntimeMatchReplay.cpp:13,203-206,243-246`）。
- 记录包络：tag(u1, 1..6) + sequence(u64) + payloadSize(u32) + payload + 32 B SHA-256；每条包络与前一条链接 SHA-256；读回时重算链哈希比对，不符即失败（`RuntimeMatchReplay.cpp:217-223,262-282`）。
- 必须存在 `Finish` 记录，以区分完整录制与中断文件（`RuntimeMatchReplay.h:45-47`）。

### 7.2 头部与记录

**头部 `RuntimeMatchReplayHeader`**（`RuntimeMatchReplay.h:15-23`）：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `initialTick` | int | 起始 tick |
| `fixedTickHz` | int | 固定步频，默认 30 |
| `compatibility` | u64 | 兼容哈希（规则 / 美术 / AI INI 文本 + 地图 + 模式规则覆盖 + 模拟 / 命令版本） |
| `initialHash` | u64 | 初始世界权威哈希 |
| `config` | string | 序列化运行配置 |
| `initialState` | string | 初始世界状态文本 |

**记录类型 `RuntimeMatchReplayRecordKind`**（`RuntimeMatchReplay.h:25-27`）：`Initial=1`, `Command=2`, `Step=3`, `Reset=4`, `Finish=5`, `Selection=6`。

**记录 `RuntimeMatchReplayRecord`**（`RuntimeMatchReplay.h:29-43`）：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `kind` | enum | 记录类型 |
| `tick` | int | 记录所属 tick |
| `stateHash` | u64 | 检查点哈希；Step 记录为 0 时推迟到下一检查点验证；Initial / Reset / Finish 必须非零 |

| `selection` | int32[] | 选择集（Selection 记录） |

### 7.3 事件快照契约

`RuntimeReplayEventSnapshot`（`RuntimeReplayEventSnapshot.h:11-46`）记录一次玩法事件的定位与归属信息：`sequence`, `tick`, `kind`, `objectId`, `targetObjectId`, `projectileActorId`, `commandVerb`, `selectedCount/acceptedCount/rejectedCount`, `commandTargetCell`, `missionFrom/missionTo/reason`, `weaponId/weaponSlot/projectileId/projectileImageId/warheadId`, `lifecycleState`, `spawnTick/impactTick/expiredTick`, 渲染意图 id / 哈希及 trailer / impact / warhead 影响意图，`sourceCell/targetCell/currentCell`，超武 id / 事件 / 第二目标格。配套 `RuntimeSnapshotCell{x,y}`（`RuntimeReplayEventSnapshot.h:6-9`）。

回放会话本地态 `RuntimeMatchReplaySession`（录制 / 查看 / 暂停 / 结束 / 失败 / 待重置 / 速度 / 选择集 / 文件流 / writer / reader / 头部），**不作为世界权威序列化**（`RuntimeMatchReplaySession.inl:1-22`）。

### 7.4 恢复一致性校验（佐证）

一致性夹具在同一非空确定性 fixture 上对三条恢复路线做权威文本逐字节对照（`RuntimeRecoveryConsistencySmoke.inl:30-64,118-142`）：

- 权威文本覆盖：完整权威哈希及其分域名、对局终局标志、`writeRuntimeMatchScore` 计分、`writeRuntimeComputerMining` 采矿、资金、生产队列、工厂投递、特殊机制（含定时炸弹）、AI 户级状态、按实例 id 排序的对象记录（归属 / 类型 / 存活 / 生命 / 坐标）。
- 三条路线恢复后权威文本必须与初始参考相等；随后相同命令与固定步推进 96 个 tick，四条轨迹（原始 + 三路线）逐 tick 相等（`RuntimeRecoveryConsistencySmoke.inl:131-161`）。
- 被拒样本：截断、外层版本、计分 Schema、采矿字段、生产校验和、定时炸弹字段、缺失现代段；回放另校验权威哈希篡改、零检查点、负检查点 tick、地图上下文不符；网络快照另校验摘要位翻转。所有拒绝必须保持整活世界与存储不变（`RuntimeRecoveryConsistencySmoke.inl:170-225`）。
- 旧域可选段缺失按原始清空默认接受；当前回放 / 网络哈希仍绑定这些域，缺失可选域不能绕过当前校验和（`RuntimeRecoveryConsistencySmoke.inl:227-255`）。
- 夹具汇总：外层存档 v14、外层快照 v15、回放格式 v1；`replay-recorder-viewer=not-integrated`、`full-application-L1-L4=not-run`（`RuntimeRecoveryConsistencySmoke.inl:258-261`）。

## 8. 确定性哈希在保存 / 同步 / 恢复中的作用

### 8.1 哈希原语

`runtime_authority_hash`（`src/core/determinism/RuntimeAuthorityHashPrimitives.h:10-77`）：

- 字符串 FNV-1a：偏移基数 `1469598103934665603`，素数 `1099511628211`（`RuntimeAuthorityHashPrimitives.h:21-28`）。
- 混合：`hash ^= value + 0x9e3779b97f4a7c15 + (hash<<6) + (hash>>2)`（`RuntimeAuthorityHashPrimitives.h:30-34`）。
- bool / 无符号 / double 混合；NaN 规范为 `0x7ff8000000000000`，零值为 0（`RuntimeAuthorityHashPrimitives.h:46-71`）。
- 规范标识：去空白 + 大写（`RuntimeAuthorityHashPrimitives.h:73-77`）。

### 8.2 世界哈希

`GameWorld::deterministicSimulationStateHash()`：模拟承载世界状态的规范、与插入顺序无关哈希。参与项：活地形 / 资源数据、地形物件、 smudge、航路点、权威对象字段（含当前被模拟消费的旧渲染位姿与工厂出口窗）；导入镜像、派生计数器、诊断与纯视觉动画缓存不参与（`src/world/model/GameWorld.h:377-383`）。夹具对照直接比对该世界哈希（`RuntimeRecoveryConsistencySmoke.inl:138-139`）。

### 8.3 规则细节哈希

`runtimeDetailRulesHash(rules)`：`RulesDatabase::loadFromIni` 时缓存一次，不每 tick 扫描全部规则（`RuntimeDetailRulesHash.h:9-10`）。内容前缀 `FunctionalDetails/1`，覆盖 Mod 扩展规则哈希、建造时间、采矿 / 卸载节奏、地形通行、战斗残骸、超时空延迟、乘员逃生、电脑采矿、电脑基地建造、电脑战术、弹道散布 / 抛体重力 / 涡轮、维修 / 退款，以及按 id 排序的地形 / 单位 / 建筑 / 武器 / 弹头 / 抛体 / 超武细节字段；末尾 FNV-1a（`RuntimeDetailRulesHash.h:11-129`）。

### 8.4 回放兼容 / 状态哈希

- `runtimeMatchReplayCompatibility(config)`：混合模拟版本串 `ConcordRTS/ReplaySimulation/45`、玩法命令版本、实际挂载的 Rules/Art/AI INI 文本（非较小的细节缓存）、地图文件字节、模式规则覆盖文件字节；哈希为 0 时回退 1（`RuntimeMatchReplayRuntime.inl:3,23-53`）。
- `runtimeMatchReplayStateHash(state)`：每步 / Reset / Finish 记录写入 `record.stateHash`；恢复后重算并与记录比对（`RuntimeMatchReplayRuntime.inl:76,126,169,232-233`）。
- 模拟版本串在确定性模拟语义变化时递增（`RuntimeMatchReplayRuntime.inl:1-3`）。

### 8.5 计分哈希

`RuntimeMatchScoreState` 为按规范屋归属排序的 `map<string, RuntimeMatchScoreEntry>`（`RuntimeMatchScore.h:11-22`）。条目：`unitsDestroyed / structuresDestroyed / unitsLost / structuresLost / score / built`。构建事件 `RuntimeMatchScoreBuildEvent{owner, count=1}`；摧毁事件 `RuntimeMatchScoreDestructionEvent{lostOwner, creditedOwner, structure, cost}`——主机过滤战役 / 已结束 / 中立 / `DontScore` 退出并解析盟友；空 `creditedOwner` 只记损失；事件累计不去重（`RuntimeMatchScore.h:24-36`）。`hashRuntimeMatchScore` 对计分状态取哈希（`RuntimeMatchScore.h:42`）；计分序列化 / 加载与夹具逐字节对照见 `RuntimeMatchScore.h:38-41`、`RuntimeRecoveryConsistencySmoke.inl:37`。

### 8.6 同步侧哈希与指纹清单

| 哈希 / 指纹 | 作用 | 出处 |

## 9. 未实现 / 平台边界

1. **非 Windows 网络 / TLS**：TLS 后端为 Windows Schannel；Linux / macOS 无 TLS 实现，非 Schannel 平台各入口返回明确不支持（`RuntimeInternetTlsTransport.cpp:1837,1847,1871,1885`）。完整 Linux / macOS 游戏及其窗口、音视频、GPU 后端尚未构建运行（`README.md:13,27`；缺口表 #1）。
2. **互联网服务端部署依赖**：联机协议与服务代码在源码内，但服务端、证书、客户端凭据需自行部署配置；不兼容原版 Westwood Online；示例域名 / 凭据为占位符（`README.md:578`；`RuntimeInternetCoordinator.h:12-15`）。
3. **UDP 数据面边界**：服务宿主不开 / 不播发 / 不转发 UDP；UDP Punch/Ack 仅证明候选可达，不构成 TCP 玩法会话连接（`RuntimeInternetServiceHost.h:107-110`；`RuntimeInternetConnectivity.h:274-276`）。
4. **回放录制 / 查看器集成**：一致性夹具标注 `replay-recorder-viewer=not-integrated`；完整应用层 L1–L4 未在该契约中运行（`RuntimeRecoveryConsistencySmoke.inl:261`）。
5. **快照压缩**：v1 禁用压缩；未来压缩 schema 须单独限制解码字节（`RuntimeMultiplayerSnapshotTransfer.h:41-45`）。
6. **排名 / 社区持久化**：纯裁决与内存状态在源码内；积分授予、clan 原子持久化属于服务侧适配器职责（`RuntimeInternetRankedMatch.h:70-72`；`RuntimeInternetServiceHostConfig.h:79`）。
7. **测试夹具排除**：`src/network/*/diagnostics/`、`src/runtime/persistence/diagnostics/`、`src/runtime/replay/diagnostics/` 下 `Smoke` / 诊断文件仅用于对照与格式佐证，不构成生产行为。
